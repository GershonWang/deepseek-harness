# Agent Note: 多版本工具链条目的更新语义

Status: implemented

[English](2026-09-14-toolchain-multiversion-update-semantics.md) | 中文

## 问题

市场的多版本清单在 2026-09-14 上线，当天实跑的用户就撞进了死胡同：装好 JDK `8u504` 后被告知有更新，点更新下载了 `21.0.12.1`，激活的却仍是 `8u504`，更新横幅继续显示，界面还报告成功。这是三个缺陷叠加。生产代码从未传过 `InstallOptions.Activate`（`AUDIT.md` N7）。目标版本已在磁盘上时 `InstallTool` 提前返回，于是第二次点击什么都不会发生。`HasUpdate` 用字符串不等把当前激活版本与清单的推荐条目相比，任何被刻意固定的旧版本都会永久显示「可更新」（N20）。相邻的第四个缺陷让「卸载激活版本」去激活字母序最大的剩余版本，在 `8u504`/`17.0.20.1`/`21.0.12.1` 这组标签下选中 JDK 8（N21）。

## 决策

三处改动，一套语义。

**更新即激活。** `UpdateAllTools` 与卡片上的显式安装都传 `Activate: true`，且 `InstallTool` 在「目标已安装」的提前返回路径上也要尊重它——「下载完成但未激活」因此在下一次点击时收敛，而不是永远不收敛。默认规则仍由 `activate || !hadOther` 决定：首次安装自动激活，未要求激活地并存安装第二个版本则不覆盖当前选择。

**「可更新」按版本号比较。** 新增 `internal/toolchain/version.go` 提供 `compareVersions`，`HasUpdate` 变成「推荐版本严格高于当前激活版本」。`current` 软链缺失时仍报可更新，横幅因此兼作修复入口。`InstalledVersions` 用同一个比较器降序排列，下拉不再出现 `17.0.20.1`/`21.0.12.1`/`8u504` 这种字母序。

**卸载回退按版本号而非字母序。** `fallbackVersion` 优先回到清单里的推荐版本（仍在时），否则取数值最高的剩余版本；工具已不在清单里（孤儿目录）时同样走数值最高。

更新会把被替换的版本留在磁盘上——多版本并存正是这份清单携带多个版本的原因——完成通知会写明这一点并点出目标版本。横幅承载每个工具的目标版本（`JDK (Temurin) → 21.0.12.1`），因为市场卡片只有约 170px 宽，放不下这句话；卡片徽标保持短文案「可更新」，目标版本放在它的 tooltip 里。

## 版本比较规则

标签来自各家发行标签：`1.23.2`（Go）、`21.0.12.1`（Temurin 21）、`8u504`（Temurin 8 的标签）。`compareVersions` 以 `.`、`-`、`+`、`_` 分段，段内每个数字串按出现顺序各占一段（`8u504` 拆成 8 与 504，JDK 8 的 build 更新因此可比），缺失的段按 0 补齐，所以 `1.2` 等于 `1.2.0`。整串不含数字时退回字节序比较，而不是凭空发明一个顺序——调用方需要的是稳定且可解释的次序，而用字典序回答「谁更新」比给出有文档的兜底更糟。预发布后缀不在建模范围内：`1.0.0-rc1` 会排在 `1.0.0` 之后，因为 `rc1` 贡献了 1。清单当前没有此类标签，代码里写明了这条边界。

## 备选方案

**更新后删除被替换的版本。** 这符合单版本的直觉，但会摧毁多版本清单存在的意义：固定用 JDK 8 的项目会因为一次无关的点击而失去它。因此选择保留，并在通知里点明目标版本。

**保留字符串比较，只改徽标措辞。** 徽标变得诚实（「非推荐版本」），但死胡同仍在：提示依旧无法被兑现，而且清单的推荐条目仍被当作「更新」，哪怕它低于用户正在跑的版本。

**不再为被固定的版本提示，并增加「忽略此版本」偏好。** 这是打扰最少的一种，但需要新的持久化状态、设置入口，以及「忽略何时失效」的规则。而眼前的缺陷——一个点了也不产生任何变化的提示——不需要这些就能修好。

**只给 JDK 8 开特例，其余保留字母序回退。** 把发行方的标签知识塞进卸载路径，正是当初出错的地方。一个小的比较器同时服务判定、展示与回退，并由一张表驱动的用例覆盖。

## 后果

死胡同封上了：更新会下载、会切换、横幅会消失。刻意跑旧版 JDK 的用户仍会看到「可更新」——现在带着目标版本——因为那才是诚实的状态；变化在于对它采取行动会得到承诺的结果。

`compareVersions` 成为判定、展示与回退唯一的排序权威，将来的标签风格只需满足它一处。它记录在案的边界是预发布后缀与不含数字的标签。

多版本并存仍然意味着磁盘上有几份完整副本（两个 JDK 条目约 103 MB 与 207 MB），没有任何机制自动清理它们；卡片上的按版本卸载是唯一的清理路径。

## 测试

`TestCompareVersions` 固定比较规则，含跨风格的 `8u504` 与 `21.0.12.1` 以及字节序兜底。`TestHasUpdate_VersionOrder` 覆盖低于、等于、高于推荐版本以及软链缺失。`TestUninstall_FallbackByVersionOrder` 固定回退的两条分支。`TestToolStatuses_InstalledVersionsOrderedByVersion`、`TestSortVersionsDesc` 与 `TestHighestVersion` 固定排序。`TestInstallTool_AlreadyInstalledHonorsActivate` 固定激活的两条分支。`TestUpdateAllTools_ActivatesRecommendedVersion` 用临时 home 预置两个版本、全程不联网地驱动真实的 `UpdateAllTools`；把 `Activate` 改回 `false` 时它以 30 秒超时失败——接线是这样验证的，而不是假定的。
