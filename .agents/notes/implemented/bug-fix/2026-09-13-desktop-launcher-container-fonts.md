# Agent Note: Container fonts and fontconfig injection for the desktop launcher

Status: implemented

English | [中文](2026-09-13-desktop-launcher-container-fonts.zh.md)

## Problem

In the packaged desktop client, time text such as `6分32秒` or `17小时53分` renders with the digits and the CJK characters pressed into each other, while the same page renders correctly in Chrome. The defect reproduces only under WebKitGTK: inside the Linglong container every family in the CSS font stack is missing, so the stack falls through to one family that covers Latin and CJK together (Source Han Sans). A single set of metrics then serves both scripts on the same line, and the glyphs collide.

Registering fonts and aliases on the packaging side alone cannot fix this. A host user-level fontconfig file (`~/.config/fontconfig/conf.d/99-deepin.conf`) redirects `sans-serif` to Source Han Sans with `prepend` plus `binding="strong"`, which outranks any alias `<prefer>`, and the tail of the CSS stack is exactly `sans-serif`.

## Decision

The package ships Noto Sans Display (Latin) and JetBrains Mono (monospace, with the Regular weight added) into `${PREFIX}/share/dsh-fonts`. Neither `usr/` nor `etc/` inside a layer enters the container namespace, and `usr/share/fonts` is additionally shadowed by a host mount, so the conventional font directory is unusable.

Before WebKit initializes, the launcher points `FONTCONFIG_FILE` at `etc/fonts/dsh-fonts.conf`, generated by `linglong/install-container-fonts.sh`. That configuration includes the system configuration, declares a writable `<cachedir>` (the container's `/var/cache/fontconfig` is read-only), registers the shipped font directory, and aliases the family names used by the CSS stack to the shipped fonts. `internal/packaging/fontconfig.go` decides whether to inject the variable and calls it before `wails.Run`, because GTK and WebKit read `FONTCONFIG_FILE` during their first initialization; an unpackaged run leaves it unset rather than pointing at a relative path.

The CSS stack is part of the fix, not an alternative to it. `packages/client/ui-theme/src/styles/base.css` puts `'Noto Sans Display'` and `'WenQuanYi Micro Hei'` at the front of `--dsw-font-family` and `'JetBrains Mono'` at the front of `--ds-font-family-code`. `--dsw-font-family` is the base family of every `--dsw-font-*` typography token, 33 component files consume those tokens, and the time text uses `--dsw-font-xs-13`, which derives from it.

Measured alias reach with the shipped configuration: `sans-serif`, `BlinkMacSystemFont`, `PingFang SC`, `Hiragino Sans GB`, `Microsoft YaHei`, `Helvetica Neue`, `SF Mono`, `Fira Code`, `Menlo`, and `Consolas` all resolve to a shipped font. `-apple-system` is a fontconfig built-in fallback that no alias changes (`fc-match` returns the host default). `monospace` is pinned by the system configuration, and the CSS monospace stack contains no bare `monospace`, so no alias is declared for it.

## Alternatives considered

**Register the fonts and aliases on the packaging side only, leaving the CSS stack alone.** The host user-level configuration redirects `sans-serif` with `prepend` plus `binding="strong"`, which outranks an alias; measured on the current host, both `-apple-system` and `sans-serif` landed on Source Han Sans and the collision persisted. Rejected.

**Install the fonts under `usr/share/fonts`.** A layer's `usr/` does not enter the container namespace, and `usr/share/fonts` is covered by a whole-directory host mount, so the shipped fonts would never be read. Rejected.

**Take the CJK family from the `fonts-wqy-microhei` apt dependency.** Exported product layers and the base layer contain no wqy or Micro Hei entity at all; the CJK fallback that actually renders comes from the host mount. That dependency neither enters the package nor changes the runtime, and the mismatch stays tracked as an open item. Rejected as the mechanism.

## Consequences

When the host already has a font with the same family name (Source Han Sans, Microsoft YaHei), fontconfig matches by family name and selects the host copy, so the shipped font is not chosen. This affects only how the machine that already has the font looks, not behavior on machines that lack it.

`fc-match` reports what fontconfig resolves, while WebKit chooses the rendering font through its own engine logic; the two can differ. The gap was closed by hand: after repacking `0.1.2.7` and installing it, the time text no longer collides.

The shipped configuration and the configuration that actually took effect inside the container were diffed line by line, and the only difference was the dropped `monospace` alias. Running `fc-match` with both configurations over the 17 candidate family names of the CSS stack returned identical results (`sans-serif` to Source Han Sans, `BlinkMacSystemFont` and `PingFang SC` to `NotoSansDisplay-Regular.ttf`, the monospace families to `JetBrainsMono-*.ttf`).

## Testing

`go test ./internal/packaging/` covers the `FONTCONFIG_FILE` decision, including the unpackaged prefix that must stay unset. `sh -n` checks the generator script's syntax. The ui-theme suite runs 81 tests, with one pre-existing failure unrelated to this change.
