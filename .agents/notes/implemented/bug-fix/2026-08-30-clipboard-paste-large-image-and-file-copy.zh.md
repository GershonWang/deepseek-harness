# Agent Note: 壳剪贴板粘贴支持大图与文件复制

Status: implemented

[English](2026-08-30-clipboard-paste-large-image-and-file-copy.md) | 中文

## Problem

打包版 dsh-desktop-launcher 的剪贴板粘贴路径存在三个缺陷：

1. **大图粘贴成空白。** 从聊天应用复制的图片（例如微信右键"复制图片"）进入输入框后变成灰色空白占位块。X11 剪贴板桥接读到的选择内容是一份损坏、被截断的缓冲区：537,485 字节的 PNG 只读回 13,200 字节且没有 IEND 块，浏览器无法解码。

2. **复制图片文件毫无反应。** 在文件管理器中复制图片文件（右键复制或 Ctrl+C，会向 X11 CLIPBOARD 写入 `text/uri-list`）再粘贴到输入框没有任何效果：没有附件、没有文本、也没有报错。

3. **复制含特殊字符的图片文件毫无反应。** 即使桥接已被咨询，文件名含空格或括号（例如 `火山引擎邀请海报 (1).png`）的文件仍无法粘贴。DDE 文管会在 `text/uri-list` 中把这类名称做百分号编码（空格变 `%20`、括号变 `%28`/`%29`），桥接把编码后的路径当作字面文件名处理，于是 `os.Stat` 失败，读取返回空。

剪贴板桥接是 WebKitGTK 壳中粘贴图片的唯一通道——引擎永远不会把剪贴板位图暴露给页面——所以这些缺陷都在这一路径上。

## Decision

**读取完整的回复载荷。** X11 线协议回复头的 length 字段是位于字节 4-7 的 CARD32（以 4 字节为单位）。Go 客户端此前只读取低 16 位（`binary.LittleEndian.Uint16(hdr[4:6])`），于是任何超过 65,535 字（262,140 字节）的回复都会被静默截断为 `(length & 0xFFFF) * 4` 字节。`readReply` 现在用 `binary.LittleEndian.Uint32(hdr[4:8])` 读取 length。大剪贴板图片（截图、聊天图片）恢复完整传输。

**在文件项之前先咨询壳桥接。** Web 输入框捕获阶段的粘贴处理器此前一看到粘贴事件带有 `kind: 'file'` 且类型为 `image/*` 的文件项就会短路返回，把处理交给 Lexical。WebKitGTK 会把文件复制粘贴（`text/uri-list` 选择）暴露成文件项，但容器侧引擎无法提供这些文件字节，于是 Lexical 什么都没插入。处理器现在总是先问壳桥接——桥接既能读位图选择，也能读指向可读图片文件的 `text/uri-list`——只有桥接没有图片时才回退到已交付的文件项或纯文本。这让文件管理器复制能落成附件。

**解码文件 URI 中的百分号转义。** `uriToPath` 现在对 `file://` URI 的路径部分做百分号解码（RFC 3986 的 `%XX`），让含空格、括号或其他保留字符的文件名能解析到真实文件系统路径。只解码 `%XX` 转义；字面 `+` 保持为 `+`，因为文件路径不是表单编码。同时修正了无效的主机分支：`file:///path` 保留其路径，`file://localhost/path` 去掉本地主机，其他主机一律拒绝。

## Testing

Go 改动已对真实 X11 服务器验证：从真实剪贴板读取 537,485 字节的 PNG 会返回以 IEND 结尾的完整缓冲区，此前只返回 13,200 个截断字节；读取 `火山引擎邀请海报 (1).png` 的百分号编码 `file://` URI 会返回完整的 316,319 字节文件。单元测试钉住了 `uriToPath` 的解码行为（空格、括号、`%` 自身、非法转义、`+` 保留、主机处理）。现有协议测试（假服务器）全部通过。Web 改动由现有 ui-conversation 套件（349 个测试，含 `desktop-clipboard` 与输入框粘贴路径）以及干净的 typecheck 覆盖。

## Alternatives considered

**映射请求方窗口。** 在排查空白图片时考虑过（之前的修复为消除左上角闪现而停止了映射 8×8 请求方窗口）。在真实服务器上做映射与未映射对比，两种方式都读到同样的 13,200 个截断字节，证明截断是回复长度 bug 造成的，与窗口状态无关。大图读取不需要任何映射改动。

**保留文件项提前返回，只放宽它的条件。** 已否决，因为容器无法依赖 WebKitGTK 交付被其扣留的选择中的可用文件字节；壳桥接是位图与 uri-list 剪贴板内容唯一可靠的读取方。

**用 `net/url` 的表单解码器。** 已否决，因为 `url.QueryUnescape` 会把 `+` 变成空格，破坏合法包含 `+` 的文件名。手写的 `percentDecode` 只解码 `%XX`，其余字符原样保留。

## Consequences

粘贴大图（超过 262 KB 的截图、聊天图片）正常工作并完整渲染。在文件管理器中复制图片文件后粘贴，当容器能读取该文件路径（通常是挂载的家目录）时会落成附件，包括含空格、括号或非 ASCII 字符的文件名。容器读不到文件路径的粘贴会回退到已交付的文件项，与之前的无操作一致，且不会让纯文本粘贴回退。纯文本粘贴不变。
