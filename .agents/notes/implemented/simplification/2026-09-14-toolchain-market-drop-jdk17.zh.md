# Agent Note: 工具链市场下架 JDK 17

Status: implemented

[English](2026-09-14-toolchain-market-drop-jdk17.md) | 中文

## 问题

清单在 2026-09-14 扩到三个 JDK 版本（`21.0.12.1`、`17.0.20.1`、`8u504`），这是多版本那条路第一次承载产品数据。随之上线并至今未修的多版本缺陷有三个：「全部更新」下载了推荐版本却从不激活（`AUDIT.md` N7）；`HasUpdate` 比的是推荐条目而不是版本序，于是被刻意固定旧版本的工具永久显示「可更新」（N20）；`Uninstall` 回退到字母序最大的剩余版本（N21）。

当天实跑市场的用户正好撞上前两条：装好 8u504，卡片与横幅提示可更新，点更新，21 的归档下载完成——然后磁盘上两个版本并存，激活的仍是 8u504，更新横幅继续显示。用户点什么都没用：第二次点击发现目标版本已安装便提前返回，却依旧报告成功。

## 决策

`jdk21` 保留推荐条目 `21.0.12.1` 与 `8u504`，从 `internal/toolchain/tools/index.json` 移除 `17.0.20.1`，`description` 改为「可选 8 / 21」。`21.0.12.1` 这一串逐字不变，因为它决定安装目录 `jdk21-21.0.12.1` 与 `current/jdk21` 软链的指向。

动机是把三个未修缺陷的作用面从三个版本标签压到两个，而不是 JDK 17 本身有故障：2026-09-14 实测其归档地址返回 `HTTP/2 302`，`url`/`sha256`/`size` 三个字段未被改动，只是不再提供该版本。

保留两个版本而不是收敛到一个，是为了在修 N7、N20、N21 期间让多版本链路继续承载真实产品数据：单版本清单会把这条链路打回「从未被走过」的状态，而那正是这些缺陷当初能上线的条件。

`frontend/tools/preview.mjs` 与两份启动器 README 都写明了当时可选的三个版本，已随本次下架同步。`linglong/tools.yaml` 只登记每个工具的推荐版本，从未带过 17，无需改动；`verify-tools.sh` 比对的是工具 ID 而非版本列表，`catalog_test.go` 也没有 17 的断言。

## 索引的重新发布

客户端真正读取的清单不是这个文件：`internal/toolchain/remote.go` 把 `defaultIndexURL` 钉在提交哈希而不是分支上。本次下架重走了 `92d150b3cb` 做过的重钉：`defaultIndexURL` 现指向 `ff0b924d11a2ca5cef4a908bec0ec54282ae7dc8`，该提交的 `index.json` blob（`599f8341…`，由 `git rev-parse <commit>:apps/desktop-launcher/internal/toolchain/tools/index.json` 取得）与工作区一致，实跑其 raw 地址返回 HTTP 200 且 sha256 相同。在该提交之前发布的启动器，要等到带这次重钉的版本发布才不再提供 17。

## 后果

已经装过 `jdk21-17.0.20.1` 的机器保留它：`ListVersions` 扫描目录而不是查询清单，因此该版本仍可通过卡片下拉切换与卸载。它只是从「可安装版本」列表里消失；又因为 N20 未修，仍激活在 17 上的机器继续显示「可更新」——与 8u504 用户看到的措辞相同。

这次下架买到的是三个未修缺陷更小的暴露面，以及后续修复更小的改动面；付出的是面向 JDK 17 的项目在 17 回到清单前无法再从市场安装该版本。

## 备选方案

**先修 N7、N20、N21，三个版本都留着。** 那才是真正的修复，而且改动更大：涉及激活语义、更新比较、卸载回退三处及其测试。现在下架一个版本并不妨碍它，反而阻止当天的用户可见故障扩散到第三个版本标签。

**连 `8u504` 一起去掉，回到每个工具一个版本。** 那会把多版本的作用面清零，但 JDK 8 正是这个工具需要多版本的原因；单版本清单会让版本下拉、`SetActiveVersion` 与按版本卸载都没有产品数据，也就是让这些缺陷当初未被察觉的那个状态。

**也从 `linglong/tools.yaml` 里删掉 17。** 无处可删：该文件每个工具只登记一个推荐版本，多版本的其余条目只存在于 `index.json`。

**先按住本地改动，等重钉能与 N7/N20/N21 的修复一起发。** 这样每个提交里，git 中的清单与客户端读取的清单都一致。之所以不这么做，是用户要求现在就收窄版本面；重钉仍是独立一步，并在 `AUDIT.md` N25 里记为待办。
